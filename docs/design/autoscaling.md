# Kubernetes autoscaling (phase 6)

Drafted and agreed 2026-10-18, with the open questions settled as proposed.

Goal: on Kubernetes, **a HorizontalPodAutoscaler grows the cluster under
load, and nodes can be removed, while clients read and write**, with no
write lost, no key served by two nodes, and nobody typing `STUART`
commands. Kubernetes decides how many nodes there are; stuart decides
which slots each owns (phase 4's decision). Phase 5 moves the slots; what
is missing is that nothing starts the moves by itself, nothing reports the
load, a node has no memory limit, and there are no manifests.

How it fits together:

- **The nodes are a StatefulSet** of one-core pods (`requests` =
  `limits`: one CPU, and memory), behind a headless Service so that each
  has a stable name: `speedvault-3.speedvault.<namespace>.svc:7000` is what it announces
  and what clients are redirected to. A pod that restarts comes back with
  the same name and a new id, which stuart already treats as a
  replacement. `podManagementPolicy: OrderedReady` removes pods one at a
  time, so scale-downs drain one node after another; a
  PodDisruptionBudget (`maxUnavailable: 1`) does the same for evictions.
- **stuart is a one-replica StatefulSet** with its state file on a
  PersistentVolume. If its pod is rescheduled, traffic flows on and
  scaling waits (stuart replicated is phase 8).
- **stuart drives itself** (`--auto`): it keeps the slots even over the
  nodes that are up and not leaving. A node that joins gets its share; a
  node that leaves is drained, then removed from the table; slots left
  unassigned by a node that was replaced go to the nodes (empty: their
  keys died with the node). No `REBALANCE` or `DRAIN` by hand, and no
  "refused while slots move": stuart plans again whenever the nodes
  change, moves under way finish, queued ones are planned again.
- **A node drains itself on SIGTERM**: it sends `STUART LEAVE id`, serves
  on while its slots move away, and exits once stuart has removed it from
  the table (or the drain timeout passes, or a second signal comes).
  `terminationGracePeriodSeconds` is sized for a full node to drain. With
  no persistence, draining is the only way a pod can stop without losing
  keys, so a node drains on *every* SIGTERM: a scale-down, an eviction, a
  rolling update (each pod's keys move out, then back in once it
  restarts).
- **Scale up automatically, scale down by hand** (as the outline says):
  the HPA adds at most 2 pods per 5 minutes after a 60 s window, on the
  node's own busy CPU and on its memory against `maxmemory`, both at 70%;
  `scaleDown.selectPolicy: Disabled`. `kubectl scale` scales down, a node
  at a time. The 30% left is room for the moves: a new node relieves the
  others only once its slots have arrived.
- **Metrics through Prometheus**: each node and stuart serve
  `/metrics`; the Prometheus adapter makes the busy CPU and the memory
  custom metrics the HPA reads. Not the container's CPU (busy-polling
  makes an idle node look busy) and not its memory (the allocator keeps
  pages after keys expire).
- **Clients** reach the nodes inside the Kubernetes cluster by their
  names (as with a Redis Cluster on Kubernetes). Their seed is a Service
  over the nodes (`speedvault-seed:7000`), which works for every client
  including Lettuce, so stuart's `CLUSTER NODES` stays as it is (no
  `myself` line).

Open questions:

- **Draining on every SIGTERM.** Proposed, since without persistence a pod
  that stops without draining loses its keys. The cost: a rolling update
  moves every node's keys out and back in, one node at a time. The
  alternative (exit at once on a rolling update) would need a way to tell
  them apart, which Kubernetes doesn't give the pod.
- **Nodes that are gone for good.** A pod removed without draining (the
  grace period ran out, its machine died) stays `down` in stuart, its
  slots unserved, until `STUART FORGET`. stuart can't tell a dead node from
  one it can't reach, and giving away the slots of a node that still
  serves them would put a key on two nodes, so this is proposed manual.
  Watching the pods through the Kubernetes API would know for sure; that
  needs RBAC and a client in stuart, so it isn't in this plan.
- **Eviction.** Only `noeviction` (reject writes) is proposed: as a store
  that scales out, the answer to being full is another node. Redis's
  `allkeys-lru` and the other policies (for cache use) would come later.
- **Metrics path.** The Prometheus adapter, as the outline says. KEDA
  reads Prometheus too and is simpler to set up; HPA on plain container
  CPU works only with `--busy-poll 0` (about 0.9× Redis unpipelined
  instead of 1.4×) and plain container memory overcounts. Proposed: the
  adapter, with KEDA documented as an alternative.
- **Kustomize or Helm.** Plain Kustomize manifests first (nothing to
  install, easy to read); a Helm chart, which most people expect, after
  this phase.
- **Balancing by slot count.** The planner evens out slots, not memory
  or load. Keys spread evenly over slots unless hash tags pile them up;
  balancing by memory (from the metrics) would come later if needed.
- **CI.** kind runs inside CI's Docker-in-Docker, but with Prometheus it's
  heavy and slow (minutes, a few GB). Proposed: milestones 1–4 in the
  usual jobs; the kind test of milestone 5 as a CI job; the full autoscaling
  test (milestone 6) run by hand and as a manual CI job.
